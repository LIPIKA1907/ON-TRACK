# OnTrack AI - Project Facts & Inventory
*For SIH2025 Problem Statement: SIH26103*

## 1. Project Summary
OnTrack AI is an offline-first, full-stack AI platform designed for the Ministry of Statistics and Programme Implementation (MoSPI). It evaluates infrastructure project parameters to predict and classify the risk of time overruns, cost overruns, and implementation failures. It provides decision-makers with live dashboards, SHAP-based risk explanations, actionable AI-driven recommendations, and an interactive "What-If" simulator to gauge the impact of management interventions.

**Modules:**
*   **Dashboard:** High-level summary of a selected project's progress, budget, timelines, and raw MoSPI records.
*   **Risk Analysis:** Displays predictive risk scores and uses SHAP values to explain the top drivers behind predicted overruns.
*   **Scenario Analysis (What-If Simulator):** Interactive sliders allowing users to manipulate project variables to instantly recalculate cost, time, and overall risk probabilities.
*   **Decision Support:** Actionable, prioritized recommendations generated by local rule engines or LLMs based on identified project risks.
*   **AI Chat:** A conversational assistant that relies on a local LLM to answer ad-hoc queries about the specific project using injected context.
*   **Early Warnings:** Live monitoring cards highlighting immediate critical indicators like schedule slippages or cost escalations.

## 2. Data
*   **Source:** Ministry of Statistics and Programme Implementation (MoSPI) PAIMANA dataset (August 2026 Snapshot).
*   **File:** `data/paimana/paimana_normalized.csv`
*   **Format:** CSV
*   **Size:** 1,731 records across 26 columns.
*   **Data Cleaning & Preprocessing:**
    *   Target Creation: Time Overrun Flag, Cost Overrun Flag, and Implementation Risk Flag derived from actual vs. approved metrics.
    *   Missing Values: Numerical features imputed with the median strategy (e.g., Milestones_Delayed); Categorical features imputed using the most frequent strategy (e.g., Contractor_Performance).
    *   Encoding/Scaling: Processed via Scikit-Learn's `ColumnTransformer` (scaling applied implicitly in tree models or strictly encoded).
*   **Train/Test Split:** 80% Training (1,384 records) / 20% Testing (347 records).
*   **Public Status:** The base PAIMANA dataset is public government data.

## 3. Feature Engineering
**Input Features (17 Total):**
*   **Numerical (14):** Approved_Cost, Planned_Duration, Elapsed_Duration, Physical_Progress, Planned_Progress, Financial_Progress, Expenditure, Milestones_Total, Milestones_Delayed, Average_Milestone_Delay_Days, Procurement_Delay_Days, Land_Acquisition_Progress, Approvals_Pending, Scope_Changes.
*   **Categorical (3):** Sector, Project_Type, Contractor_Performance.
*   **Excluded from inputs:** Project_ID, Time_Overrun_Months, Cost_Overrun_Pct, Time_Overrun_Flag, Cost_Overrun_Flag, Implementation_Risk_Flag.
*   **Derived Features (EVM Frontend):** Estimated cost and time at completion (EAC) dynamically calculated in the frontend using Earned Value Management formulas (e.g., `EAC_Cost = Expenditure / (Physical_Progress/100)`).

## 4. Machine Learning Models
**Algorithms:** XGBoost Classifier (Primary) and Random Forest Classifier (Baseline).
**Library:** `xgboost` and `scikit-learn`.
**Training File:** `ml/train_models.py`
**Evaluation Metrics (Test Set):**
*   **Time Overrun Risk (XGBoost):** Accuracy: 0.9193 | Precision: 0.9266 | Recall: 0.9439 | F1: 0.9352 | ROC-AUC: 0.9614
*   **Cost Overrun Risk (XGBoost):** Accuracy: 0.8646 | Precision: 0.6818 | Recall: 0.6338 | F1: 0.6569 | ROC-AUC: 0.8933
*   **Implementation Risk (XGBoost):** Accuracy: 0.9481 | Precision: 0.9577 | Recall: 0.9833 | F1: 0.9703 | ROC-AUC: 0.9568
*   **Saved Artifacts:** `models/time_overrun_model.joblib`, `models/cost_overrun_model.joblib`, `models/implementation_risk_model.joblib`, `models/preprocessor.joblib`.

## 5. Explainability
*   **Method:** SHAP (SHapley Additive exPlanations).
*   **Explainer:** TreeExplainer applied directly to the XGBoost models.
*   **Usage:** Calculates the marginal contribution of each feature to the final risk probability. The `ml/explain.py` endpoint aggregates these values, sorts them by absolute magnitude, and returns the top 3 drivers (e.g., `feature: "Physical_Progress", contribution: +0.12`). The frontend renders these directly as "Top Baseline Drivers" with visual impact bars.

## 6. What-If / Scenario Simulator
*   **Interactive Inputs:** Physical Progress (%) [0-100], Expenditure (Cr) [0-200% of Approved Cost], Elapsed Duration (Months) [0-300% of Planned], Milestones Delayed [0-20].
*   **Presets:**
    *   *Optimistic:* Physical Progress +20, Milestones Delayed -2
    *   *Pessimistic:* Physical Progress -15, Elapsed Duration +3, Milestones Delayed +3
    *   *Add Resources:* Expenditure +10%, Physical Progress +10
    *   *Delay 6 Mos:* Elapsed Duration +6
*   **Re-run logic:** The frontend calculates EVM magnitudes locally and sends the manipulated variables via a REST POST to `/what-if`, where the backend runs `predict_project_risk()` (in `what_if.py`) through the real XGBoost artifacts and returns updated probability deltas.

## 7. AI Chat / LLM
*   **Provider:** Ollama (Local REST API running at `http://localhost:11434`).
*   **Models:** Checks a preferred fallback list (`llama3.2:1b`, `llama3.2:3b`, `llama3.1:8b`, `mistral`, `gemma2`, etc.) and picks the first available.
*   **Retrieval Method:** **NO vector store or embeddings are used.** Information is injected dynamically by serializing the active project's metrics into a structured string block (`format_project_context`) and attaching it to the prompt.
*   **Constraints:** The system prompt explicitly commands the LLM to provide 1-2 line greetings without dumping data, answer *only* what is asked, and explicitly forbids inventing numbers.

## 8. Tech Stack & Architecture
*   **Frontend:** React 19, Vite 8, Vanilla CSS (No heavy UI frameworks like Tailwind or Material UI). Charts are pure HTML/CSS/SVG.
*   **Backend:** Python 3.10+, FastAPI, Uvicorn.
*   **Main Endpoints:**
    *   `GET /health`: System & LLM status.
    *   `GET /projects`: Fetches the PAIMANA project list.
    *   `POST /what-if`: Executes scenario prediction through models.
    *   `POST /chat`: Interacts with Ollama.
*   **Storage:** Local CSV files (`data/projects.csv`, `data/paimana_normalized.csv`). No SQL/NoSQL databases used.
*   **Architecture Diagram:**

## 12. Limitations and Future Scope
*   **Limitations:**
    *   *Data Features:* Heavy missing values in specific contractor/approval metrics required extensive median imputation, masking nuance.
    *   *RAG/LLM:* The system relies on context-window injection instead of vector embeddings, which limits the ability to query across *multiple* projects simultaneously.
    *   *Model Scope:* Magnitude of overruns is calculated deterministically via EVM in the frontend; the ML model currently only predicts the *probability* of an overrun, not its size.
*   **Future Scope:** Integrate a vector database (e.g., ChromaDB or FAISS) for multi-project semantic search; train regression models for overrun magnitude.

### 8 Likely Judge Questions
1.  **Q: How do you handle missing MoSPI data?**
    *A:* We use Scikit-Learn's median imputation for numerical data and most-frequent imputation for categorical data.
2.  **Q: Why XGBoost over Deep Learning?**
    *A:* Tabular data with 1,731 rows performs exceptionally well on gradient boosting, and it allows for native SHAP explainability.
3.  **Q: Does the AI chat hallucinate numbers?**
    *A:* No. We use strict context injection and system prompts forbidding the LLM from inventing metrics; it only reads the supplied JSON payload.
4.  **Q: Is your What-If magnitude calculation ML-based?**
    *A:* The *probability* is ML-based. The magnitude (Rs Cr / Months) is calculated using deterministic Earned Value Management (EVM) formulas to ensure strict financial accuracy.
5.  **Q: What if the internet drops?**
    *A:* The entire stack, including the LLM (via Ollama), runs locally on localhost. It is completely unaffected.
6.  **Q: How did you validate your models?**
    *A:* 80/20 train-test split evaluating Precision, Recall, F1, and ROC-AUC to handle class imbalances.
7.  **Q: Where does the data come from?**
    *A:* The official MoSPI PAIMANA August 2026 snapshot.
8.  **Q: How do I run this right now?**
    *A:* Double click `start_ontrack.bat`. It handles the python backend, node frontend, and browser launch.
